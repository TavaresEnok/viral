## Visão Geral

O CLIPIA (ViralForge) é uma plataforma de clipping de vídeo com IA, projetada nativamente para o mercado brasileiro (PT-BR). Transforma vídeos longos (podcasts, entrevistas, aulas, lives) em dezenas de clipes curtos verticais 9:16 automaticamente, com transcrição, análise LLM, legendas animadas, thumbnails e download.

Esta análise compara o CLIPIA com os 4 principais concorrentes do mercado: **OpusClip**, **Vizard AI**, **Submagic** e **Vidyo.ai**.

## Resumo do Pipeline Atual do CLIPIA

```
1. Input: YouTube URL ou upload direto (MP4, MOV, MKV, WebM até 500MB)
2. Download: yt-dlp (com proteção SSRF)
3. Extração de áudio: FFmpeg
4. Transcrição: Multi-tier
   ├── YouTube captions (fast, quality-scored)
   ├── Remote GPU ASR (Faster-Whisper turbo+int8 on CUDA)
   └── OpenAI Whisper API (fallback)
5. Análise AI: 2-pass DeepSeek pipeline
   ├── Pass 1: Pré-seleção de candidatos (temp 0.55, max 420 segments)
   └── Pass 2: Curadoria editorial profunda (temp 0.35)
6. Validação: Heurísticas PT-BR, deduplicação por overlap
7. Render: FFmpeg ou Remotion (9 layouts, 10 temas de legenda)
8. Thumbnail: Frame no start+2 seconds
9. Download: Autenticado (clipes, thumbnails, legendas)
```

### Scoring Viral Composto

```
finalScore = opening * 0.30
           + closing * 0.30
           + quotability * 0.20
           + context_independence * 0.10
           + emotional_density * 0.10
           + localBoosts (numbers, strong language, questions, strong closing)
           - penalties (high cut risk, weak ending, low text similarity, duration fora do ideal)
```

## FASE 1 — SEGURANÇA E HARDENING (Semanas 1-3)

**Objetivo:** Resolver todos os riscos de segurança identificados na AUDITORIA_CLIPIA.md e preparar a base para produção.
**Nota atual de segurança:** 4.0/10 → **Meta:** 8.5/10

### 1.1 Autenticação e Sessão

**Problema:** JWT armazenado em localStorage (vulnerável a XSS), sem refresh tokens, sem proteção contra brute force completa.

- [ ] **1.1.1** Migrar JWT de localStorage para httpOnly Secure SameSite=Strict cookies
  - Criar novo endpoint `/auth/refresh` que emite novo access token
  - Access token com TTL curto (15 min), refresh token com TTL longo (7 dias)
  - Implementar cookie rotation no refresh
  - Arquivos: `apps/api/src/auth/auth.service.ts`, `apps/web/src/stores/auth.store.ts`
- [ ] **1.1.2** Implementar refresh token rotation com blacklist
  - Tabela `refresh_tokens` no Prisma (userId, tokenHash, expiresAt, revoked, createdAt)
  - Revocar toda a família de tokens se um for comprometido
  - Arquivo: `packages/database/prisma/schema.prisma`
- [ ] **1.1.3** Completar proteção brute force
  - Usar Redis para tracking (não in-memory, que perde em restart)
  - Lockout progressivo: 5 tentativas → 5min, 10 → 15min, 15 → 1hr
  - Arquivo: `apps/api/src/auth/auth.service.ts`
- [ ] **1.1.4** Implementar device fingerprinting opcional
  - Hash de User-Agent + IP no refresh token
  - Alertar usuário se detectar login de dispositivo novo
- [ ] **1.1.5** Implementar logout global (revocar todos os refresh tokens do usuário)

### 1.2 Proteção de Rotas e Input

**Problema:** Path traversal em downloads, SSRF via YouTube URLs, validação de MIME bypassável.

- [ ] **1.2.1** Corrigir path traversal em downloads
  - Usar `safe-path.helper.ts` em TODOS os endpoints de download
  - Validar que o path resolvido está dentro de `STORAGE_ROOT`
  - Usar `path.resolve()` + `startsWith()` para verificação
  - Arquivos: `apps/api/src/clips/clips.controller.ts`
- [ ] **1.2.2** Proteger contra SSRF em YouTube URLs
  - Blocklist de IPs internos (10.x, 172.16-31.x, 192.168.x, 127.x, ::1)
  - Resolver DNS antes de fazer request e validar IP
  - Timeout máximo de 30s para yt-dlp
  - Arquivo: `apps/worker/src/services/youtube-download.service.ts`
- [ ] **1.2.3** Validação de MIME por magic bytes obrigatória
  - Não confiar no `Content-Type` do header
  - Ler primeiros bytes do arquivo e validar contra signatures conhecidas
  - MP4: `00 00 00 18 66 74 79 70` ou `00 00 00 20 66 74 79 70`
  - MOV: `00 00 00 14 66 74 79 70`
  - MKV: `1A 45 DF A3`
  - WebM: `1A 45 DF A3` (com EBML Doctype = "webm")
  - Arquivo: `apps/api/src/projects/projects.controller.ts`
- [ ] **1.2.4** Rate limiting global com Redis
  - Implementar `@nestjs/throttler` com Redis store
  - Defaults: 100 req/min por IP, 20 req/min por usuário para uploads
  - Headers `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`
  - Arquivo: `apps/api/src/app.module.ts`
- [ ] **1.2.5** Implementar idempotency keys para operações críticas
  - Header `Idempotency-Key` para uploads e criação de projetos
  - Store no Redis com TTL de 24h
  - Retorna resposta cacheada se key já existe

### 1.3 Secrets e Configuração

**Problema:** Hardcoded dev secrets, MASTER_SECRET fraco, API keys sem rotação.

- [ ] **1.3.1** Remover todos os secrets hardcoded do código
  - Search por `JWT_SECRET`, `MASTER_SECRET`, `DATABASE_URL` no código
  - Garantir que todos vêm de `process.env`
  - Adicionar validação no bootstrap que crash se env vars críticas faltarem
- [ ] **1.3.2** Implementar secret rotation para API keys de providers

  - Rotação automática quando uma key retorna 429/401
  - Arquivo: `apps/worker/src/services/api-key.service.ts`
- [ ] **1.3.3** Gerar `.env.example` completo e atualizado
  - Documentar todas as 38+ variáveis de ambiente
  - Incluir valores de exemplo seguros (não reais)
  - Adicionar validação de schema do .env com Zod

### 1.4 Logging e Observabilidade

- [ ] **1.4.1** Implementar structured logging com Pino

### 1.5 Dead Letter Queue e Resiliência

**Problema:** Jobs falhos sem retry adequado, sem DLQ, sem alertas de falha.

- [ ] **1.5.1** Configurar DLQ no BullMQ

  - Arquivo: `apps/api/src/queue/queue.module.ts`
- [ ] **1.5.2** Implementar worker para DLQ

  - Arquivo: `apps/worker/src/worker-runner.ts`
- [ ] **1.5.3** Implementar circuit breaker para providers AI
  - Se provider retorna 5xx 5x em 1min, abrir circuito por 5min

  - Arquivo: `packages/clip-analyzer/src/`
